# Personal AI Workbench：AI 雷达与学习闭环设计

日期：2026-09-02  
状态：已确认

## 背景

Personal AI Workbench 已具备本地 Vault 索引、Wiki、知识星图、知识助手和项目管理能力，但外部信息发现、持续学习、知识沉淀与实践执行仍是分离流程。用户需要的是一个服务个人的 AI 操作系统，而不是通用新闻阅读器或多人项目管理产品。

本设计增加一条完整但分阶段交付的路径：发现 GitHub 上值得关注的 AI 项目，形成可信的趋势记录，由用户选择学习对象，在独立学习工作区完成学习，再把审核后的知识写入 Obsidian Wiki，并选择性转化为实践项目和任务。

## 产品目标

- 把外部 AI 项目发现转化为可管理的学习候选，而不是制造新的信息流。
- 用本地长期采样建立可解释的日、周、月涨星数据。
- 让没有配置模型的用户仍能使用基础榜单、收藏和筛选。
- 让学习过程具备明确任务、版本来源、练习和完成标准。
- 只把审核后的正式知识写入 Wiki，避免课程过程文件污染知识星图。
- 把知识沉淀连接到实践项目，并把复盘重新带回 Wiki。
- 保持本地优先、单用户、可移植、回环地址和公开隐私边界。

## 成功标准

首阶段运行 30 天后：

- 用户每天完成热点检查的时间不超过 10 分钟。
- 系统帮助用户找到至少 4 个值得深入了解的仓库。
- 用户正式启动至少 1 个学习项目。
- 采集覆盖率、数据缺口、失败原因和推荐理由均可见。
- 项目、雷达和学习元数据可以统一备份并恢复。
- Vault 改名或移动后，可以重新绑定原有本地状态。

抓取仓库数量、生成摘要数量和页面浏览量不是最终成功指标。

## 产品原则

1. **选择优先于浏览**：热点卡片必须推动忽略、收藏、摘要或学习决策。
2. **缺失保持缺失**：无法获得的历史涨星不估算、不平均分配、不伪造。
3. **三个问题分别回答**：快速上升、长期热门、与你相关使用独立榜单，不压缩成黑盒总分。
4. **AI 是增强能力**：确定性采集与榜单不依赖模型；AI 提供相关性判断、摘要和学习内容。
5. **过程与正式知识分离**：课程、练习和学习记录留在学习工作区；Wiki 只保存审核后的知识。
6. **用户控制写入与执行**：Wiki 入库和陌生仓库代码执行都需要明确确认。
7. **可移植性优先**：不依赖 Codex 定时任务或操作系统任务计划程序。

## 范围

### 首阶段

- 可靠性基础：功能合并、稳定启动、统一备份恢复、schema 迁移和 Vault 重绑定。
- 独立的“AI 雷达”模块及总览精选入口。
- GitHub 官方接口候选发现、每日快照和本地观测涨星。
- 日、周、月视图以及快速上升、长期热门、与你相关三组榜单。
- 收藏、忽略、减少类似推荐、摘要和加入学习等卡片动作。
- 项目内部调度、启动补采、手工采集和运行记录。
- 可选 GitHub Token 与无 Token 降级模式。
- 无模型基础模式与配置模型后的相关性判断、摘要和学习任务草案。
- 每仓库独立学习工作区、固定 commit SHA 和最多 3 个活跃学习项目。

### 后续阶段

- 原生课程、测验、检索练习、学习记录和阶段总结。
- 审核后的 Wiki sources、concepts 和 frameworks 入库。
- 从完成的学习项目创建实践项目或任务。
- 实践完成后的复盘草案与 Wiki 回写。
- 在明确确认和隔离环境下运行学习实验。

### 不包含

- 多人账户、权限、评论和实时协作。
- 通用 Cron 表达式或任意任务调度平台。
- Codex、Windows 任务计划程序或其他操作系统级调度依赖。
- 把 GitHub Trending 网页抓取作为核心数据源。
- 自动执行仓库安装脚本、构建脚本或任意命令。
- 未审核的 Wiki 自动写入。
- 邮件、消息或操作系统通知。
- 将整个 Obsidian Vault 纳入知识星图。

## 用户路径

```text
每日发现候选
→ 保存仓库快照
→ 计算本地观测日/周/月变化
→ 展示三个独立榜单
→ 用户忽略、收藏或生成摘要
→ 用户选择加入学习
→ 创建独立学习工作区并固定 commit SHA
→ 完成课程、测验和小实验
→ 生成知识沉淀草案
→ 用户审核文件与差异
→ 确认写入 Obsidian Wiki
→ Wiki 索引和知识星图刷新
→ 用户选择创建实践项目
→ 完成项目并生成复盘草案
→ 确认回写 Wiki
```

## 信息架构与界面

### 总览

总览新增“今日 AI 精选”，只展示 3 个最值得关注的仓库和未读数量。该区域不承载完整筛选和历史比较，点击后进入 AI 雷达。

采集失败时在同一位置显示安全、无敏感信息的错误摘要和“重新采集”动作，不使用系统通知。

### AI 雷达

侧边栏新增“AI 雷达”，建议路由为 `/ai-radar`。页面提供：

- 周期：今日、每周、每月。
- 榜单：快速上升、长期热门、与你相关。
- 状态：未处理、收藏、已摘要、学习队列、学习中、已完成、已忽略。
- 方向：AI Agent、AI 编程、RAG/知识库/个人 AI、AI 应用与生产力。
- 手工“立即采集”、采集状态和下次运行时间。
- 推荐偏好查看、撤销和重置。

默认数量：今日 8 个、每周 12 个、每月 20 个。仓库重复上榜时复用同一仓库记录并显示连续上榜信息，不创建重复实体。

### 热点卡片

卡片的主要信息包括：

- 仓库名称、描述和 GitHub 链接。
- 当前总 Star 与本地观测涨星。
- 数据覆盖天数和缺口状态。
- 主要语言、topics、License、最近更新时间和是否归档。
- 所属关注方向和可见的推荐原因。
- 收藏、忽略、减少类似推荐、生成摘要和加入学习。

“忽略”只影响当前仓库；“减少类似推荐”保存可撤销的本地偏好信号并降低相似候选权重。

### 学习队列

最多同时存在 3 个活跃学习项目，其余候选进入队列。每个条目显示学习目标、固定 commit、当前阶段、最近活动和下一步。归档学习项目不删除来源、决策或正式知识关联。

## GitHub 数据来源

首阶段只使用 GitHub 官方 REST 接口：

- Repository Search 建立候选池。
- Repository metadata 获取当前 Star、fork、issues、语言、topics、License、归档和更新时间。
- README 只在生成摘要时按需读取。
- 正式学习开始时读取默认分支 HEAD 并固定 commit SHA。

GitHub Trending 页面虽然提供 Today、This week 和 This month，但没有受支持的 Trending REST/GraphQL 接口，因此首阶段不抓取页面。Repository Search 只能按当前 Star、fork 或更新时间等字段排序，不能按过去一段时间新增 Star 排序。

参考：

- [GitHub Trending](https://github.com/trending)
- [Search repositories](https://docs.github.com/en/rest/search/search#search-repositories)
- [Starring API](https://docs.github.com/en/rest/activity/starring)
- [GitHub REST API rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)
- [GitHub REST API best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)

### 认证与限流

系统默认允许匿名访问。用户可以在被忽略的本地配置中提供只读 GitHub Token，以提高额度和稳定性。Token：

- 不进入公开仓库、Vault、日志、活动记录或备份。
- 不传给模型或学习文档。
- 不复用未明确配置的系统 GitHub 凭据。

请求采用串行队列、ETag 条件请求、限流状态检查和 `Retry-After`/reset 时间退避。页面始终读取本地快照，不因 GitHub 临时失败而清空最后一次成功结果。

## 本地观测涨星

系统无法可靠补齐启用前的任意仓库历史涨星，因此从第一次采集开始保存当前 Star 快照。

- 日涨星：当前有效快照减去至少约 1 天前的最近有效快照。
- 周涨星：当前有效快照减去至少约 7 天前的最近有效快照。
- 月涨星：当前有效快照减去至少约 30 天前的最近有效快照。
- 基线不足时显示“数据积累中”，不输出虚假 `0`。
- 中间缺失时显示实际覆盖天数，例如“覆盖 5/7 天”。
- 电脑或服务关闭期间不尝试重建每日数据。

每日快照保留 400 天，之后只保留月度聚合。收藏、进入学习或形成正式知识的仓库永久保留完整历史。

## 排名与推荐

### 快速上升

按对应周期的本地观测 Star 增量排序。覆盖不足的仓库不与完整覆盖仓库混排；页面明确展示覆盖状态。必要时使用增量比例作为辅助信息，但不取代绝对增量。

### 长期热门

基于当前 Star、近期维护活动、是否归档、License 和仓库年龄形成确定性排序。该榜单表示持续影响力，不宣称近期增长。

### 与你相关

先通过 topics、关键词、描述、语言和归档状态做确定性初筛，再对有限候选使用可选模型分类。关注方向固定为：

- AI Agent 与多代理系统。
- AI 编程与开发工具。
- RAG、知识库与个人 AI。
- AI 应用与生产力工具。

模型必须返回结构化方向、相关性等级和简短理由。理由显示给用户并允许纠正。纠正结果形成可查看、撤销和重置的本地偏好信号。

三个榜单不合成一个黑盒总分。即使内部需要稳定排序键，界面也始终展示原始指标和推荐原因。

## 项目内置调度

调度由项目自身管理，不依赖 Codex 或操作系统任务。

设置包含：

- 是否启用。
- 每日执行时间，默认用户本地时间 08:00。
- 时区。
- 上次尝试、上次成功和下次计划时间。

执行入口：

- 服务运行期间的内部定时检查。
- Workbench 启动时发现当日未成功采集则补采。
- 用户点击“立即采集”。

调度模块与采集模块之间只有一个幂等命令接口。相同本地日期重复调用时更新当天的最新快照并保留运行记录，不创建重复日期记录。失败不标记为成功，允许后续启动补采或手工重试。

如果服务在计划时间关闭，任务不会运行；下次启动只保存当前快照，并把中间日期标记为缺口。

## 无模型与有模型模式

无模型时始终可用：

- GitHub 候选发现。
- 本地快照与三个确定性榜单。
- 方向规则筛选。
- 收藏、忽略、减少类似推荐和学习队列管理。

配置模型后增加：

- 候选相关性判断和推荐理由。
- 低成本仓库摘要。
- 学习目标草案。
- 后续课程、测验、阶段总结和知识沉淀草案。

模型通过独立接口接入。首个适配器可以复用现有知识助手兼容网关，但领域模块不读取特定供应商配置、不假设 Codex 存在，也不把模型调用写入排名的确定性核心。

## 摘要与正式学习

### 摘要阶段

摘要只读取仓库元数据和 README，回答：

- 它解决什么问题。
- 为什么当前值得关注。
- 与用户关注方向有什么关系。
- 技术栈、维护状态和 License。
- 是否值得进入正式学习。

摘要必须记录仓库 URL、读取时间和来源版本。README 是不受信内容，只能作为资料，不能成为模型或系统指令。

### 加入学习

用户从摘要明确选择“加入学习”后：

1. 读取默认分支当前 commit SHA。
2. 创建仓库独立的学习工作区。
3. 保存来源、版本、抓取时间和生成流程版本。
4. 生成待确认的学习任务草案。
5. 用户选择学习目标：理解架构、学会使用、分析设计、复刻核心能力或判断是否采用。
6. 草案确认后进入活跃学习；超过 3 个时进入队列。

首阶段停在可审核的学习入口，不自动生成完整课程或写入 Wiki。

## 原生学习工作区

核心学习功能不依赖外部 `$teach` 技能。每个仓库拥有独立工作区，建议逻辑结构为：

```text
MISSION.md
RESOURCES.md
NOTES.md
reference/
lessons/
learning-records/
assets/
workspace.json
```

后续学习模块支持：

- 与任务目标绑定的短课程。
- 高可信来源与引用。
- 检索练习和简短测验。
- 用户回答和反馈记录。
- 阶段总结与下一步。
- 一个小实验、比较分析或明确的“不采用”判断。

完成标准是在能够说明仓库架构、关键取舍和适用边界的基础上，完成一个小实验或实践任务。阅读摘要不算完成学习。

外部教学 Agent 可以作为可选适配器，但学习工作区格式和状态机由本项目定义。

## 仓库读取与代码执行安全

摘要阶段不克隆仓库。正式学习时可以对固定 commit 做只读浅克隆，并仅按学习任务选择所需源码。

仓库 README、源码、issue、配置和脚本全部是不受信内容：

- 不把仓库内容当作系统指令。
- 不自动安装依赖、运行构建、执行脚本或启动服务。
- 不把本地 Token、模型密钥、Vault 内容或项目状态发送给仓库代码。
- 第一阶段只生成实践计划。
- 后续执行需要展示命令、依赖、工作目录、网络与文件权限，并由用户确认后在隔离环境运行。

Star 数、组织身份或推荐排名都不能替代安全确认。

## Wiki 知识沉淀

学习工作区保存过程资产。完成学习阶段后，系统生成待审核的知识变更，目标限定为：

```text
wiki/sources/<repository>.md
wiki/concepts/<concept>.md
wiki/frameworks/<framework>.md
```

入库审核展示：

- 将创建或修改的文件列表。
- 每个文件的差异。
- 仓库 URL 和固定 commit SHA。
- 引用的 README 或源码相对路径。
- 抓取时间、生成时间和工作流版本。

用户一次确认一个学习阶段的整批差异。草案发生变化后必须重新确认。确认后才写入 Vault，并触发现有 Wiki 索引和知识星图刷新。

课程 HTML、测验状态、学习会话和克隆缓存不直接写入 Wiki。

## 实践项目闭环

学习完成后，用户可以选择“创建实践项目”。系统根据学习任务预填：

- 项目名称与目的。
- 要验证的假设。
- 建议任务和完成条件。
- 学习来源及 Wiki 页面关联。

创建仍需用户确认。项目完成后生成复盘草案，包含实际结果、与原假设的差异、采用或放弃决定，以及需要更新的概念或框架页面。复盘同样经过差异审核后回写 Wiki。

## 模块与接口

### RadarRepository 模块

集中管理仓库实体、快照、运行记录、推荐、决策、偏好、保留策略和版本迁移。页面、调度和 GitHub 适配器不直接读写数据文件。

主要接口：

- `getDashboard(period, filters)`
- `recordRun(result)`
- `upsertRepositories(items)`
- `recordSnapshots(items, capturedAt)`
- `setDecision(repositoryId, command)`
- `recordPreference(signal)`、`revertPreference(id)`
- `applyRetention(now)`

### RadarScheduler 模块

调度模块只理解“是否到期”和运行状态，不理解 GitHub 或排名：

- `getSchedule()`、`updateSchedule(input)`
- `start()`、`stop()`
- `runDue(now)`
- `runNow()`
- `getStatus()`

模块接受时钟和采集命令依赖，测试无需等待真实时间。

### GitHubDiscoveryAdapter

封装官方 GitHub 请求、分页、ETag、认证、限流和错误归一化：

- `discoverCandidates(scope)`
- `getRepositories(ids)`
- `getReadme(repository)`
- `getHeadCommit(repository)`
- `checkoutSource(repository, commitSha, target)`

调用方不接触 Token 或 GitHub 响应细节。

### RadarRanking 模块

纯函数模块，根据仓库、快照、周期和偏好生成三个独立榜单。模型相关性作为显式输入，不隐藏在排序模块内部。

### RepositorySummary 模块

读取经过裁剪的仓库元数据与 README，调用可选模型接口，返回带来源和版本的结构化摘要。无模型时返回明确的不可用状态，不影响雷达其他功能。

### LearningWorkspaceRepository 模块

管理学习工作区状态、最多 3 个活跃项目的不变量、文件校验、来源版本和学习产物。它不直接写入 Wiki。

### WikiLearningIngest 模块

复用现有审核后写入的思想，为学习产物生成文件计划、差异和确认令牌。确认前只读，确认后只允许写入明确批准的 Wiki 相对路径。

## 可靠性基础

AI 雷达开发前必须完成：

- 将项目管理功能合入主分支并固定唯一启动入口。
- 统一工作台运行状态的 schema 版本和迁移注册表。
- 项目数据导出、备份和恢复。
- Vault 改名或移动后的状态发现与重新绑定。
- 归档任务查看与恢复。
- Windows 下发布门禁可重复执行。

统一备份包括：

- 项目、列、任务、标签、关联和活动。
- 仓库元数据、热点快照和运行记录。
- 收藏、忽略和推荐偏好。
- 学习队列、工作区元数据和正式学习产物元数据。

统一备份不包括：

- GitHub Token、模型密钥和其他凭据。
- 仓库克隆缓存。
- 可重新获取的 README 缓存。
- 真实 Vault 文档正文。

导入先验证版本、校验和、容量与记录归属，再生成预览；用户确认后原子替换。未知版本或损坏备份不能覆盖现有状态。

Vault 状态继续使用不可逆的 Vault 标识隔离，但增加显式导出/导入和重新绑定映射。路径变化不能静默创建一个看似全新的空工作台。

## 错误处理

- GitHub 不可达：保留最后成功结果，显示陈旧时间和重试动作。
- 限流：显示安全的重试时间，调度不进行紧密循环。
- 部分仓库失败：保存成功仓库，记录失败计数，不丢弃整个运行。
- 数据基线不足：显示“数据积累中”。
- 快照有缺口：显示覆盖天数，不估算缺失日。
- 模型未配置：雷达基础功能继续工作，摘要和学习生成显示配置说明。
- 模型输出无效：拒绝保存摘要或课程，允许重新生成。
- 仓库删除或变私有：保留历史和学习状态，标记来源不可用。
- commit 不再可取：保留已有固定版本，不静默切换到新 HEAD。
- 学习工作区损坏：进入只读恢复状态，不覆盖原文件。
- Wiki 草案漂移：确认失效，重新生成差异。

所有错误使用稳定代码和安全中文消息，不向界面或日志输出凭据、绝对路径或原始敏感响应。

## 隐私与公开仓库边界

- 服务默认只监听 `127.0.0.1`。
- 公开托管构建不暴露本地采集、学习或写入接口。
- 真实热点历史、收藏、偏好、学习记录、仓库克隆和生成报告不进入仓库。
- 本地配置和凭据只保存在 ignored 文件或未来的本地凭据适配器中。
- 演示内容必须完全合成并明确标注，不得轻微修改真实历史充当演示。
- 学习资料不得包含本地绝对路径、Token、用户 Vault 内容或未批准的项目数据。
- GitHub 仓库内容视为不受信输入，不能修改系统提示、扩大权限或授权执行。

## 实施阶段

- 可选模型接口和相关性分类。
- 结构化仓库摘要。
- 固定 commit SHA。
- 独立学习工作区和任务草案。
- 最多 3 个活跃学习项目。

阶段 0–2 构成一至两个月的首阶段交付。

- 资源、课程、测验、学习记录和阶段总结。

- sources、concepts、frameworks 草案。
- 文件列表、逐文件差异和确认写入。
- Wiki 索引与知识星图刷新。
- 从学习创建实践项目。
- 项目复盘草案与 Wiki 回写。

## 测试策略

### 可靠性

- 每个存储版本的迁移和未知版本拒绝。
- 导出、预览导入、原子恢复和损坏备份保护。
- Vault 标识变化后的重新绑定。
- 凭据、绝对路径和 Vault 正文不进入备份。

### GitHub 适配器

- 使用完全合成的响应 fixture 测试分页、ETag、限流和部分失败。
- 匿名与 Token 模式。
- README、仓库删除、归档和 commit 变化。
- 不在错误或日志中暴露认证头。

### 快照与排名

- 同日幂等更新。
- 1/7/30 天基线、覆盖不足和中间缺口。
- 400 天保留与月度聚合。
- 收藏和学习仓库不被清理。
- 三个榜单保持不同语义，不出现虚假涨星。
- 偏好信号可撤销和重置。

### 调度

- 使用注入时钟测试计划时间、时区、启动补采和手工运行。
- 服务关闭期间不虚构运行。
- 失败后允许重试且不会产生重复日期记录。
- 多个触发同时发生时只运行一个采集命令。

### 学习与入库

- 固定 commit 和来源记录。
- 最多 3 个活跃学习项目。
- 无模型降级与无效模型输出拒绝。
- 仓库内容无法改变系统指令或触发执行。
- Wiki 草案变化后确认失效。
- 只写入已批准的 Wiki 相对路径。

### 前端

- 总览 3 个精选和完整雷达导航。
- 周期、榜单、状态和方向筛选。
- 数据积累、缺口、陈旧、限流和失败状态。
- 收藏、忽略、减少类似推荐、撤销和重置。
- 无模型状态、摘要、学习队列和活跃上限。
- 桌面和窄屏下的卡片与操作可访问性。

### 发布门禁

```bash
cd Workbench
npm test
npm run build
npm run privacy:scan
```

所有门禁必须通过后才能发布。测试和演示数据只能使用完全合成的仓库、指标、学习内容和路径。
